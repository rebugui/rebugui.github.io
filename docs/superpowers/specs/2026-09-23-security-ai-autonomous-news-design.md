# Security·AI news blog autonomous operation — design

## Purpose and scope
Operate rebugui.github.io as a Korean security and AI *current-issues* blog with AdSense-oriented factual quality. Automate collection, categorization, drafting, verification, constrained publication and reporting. Do not treat AdSense page checks as approval. Preserve existing Hugo/Notion/Hermes cron architecture; avoid redesigning the public theme in this phase.

## Existing system and defects
Hermes `auto-sec-blogger` cron runs daily at 08:00; disabled launchd duplicate must remain disabled. `blog-ops-watch` runs every six hours and `adsense-stabilize-check` daily. Collector currently queries only its first three security keywords in Google News; AI coverage comes incidentally from other feeds. It marks candidate URLs seen *before* evaluation/writing/Notion persistence, so a downstream failure loses retries. Selector's score >=6 is not factual verification. Notion `검토 완료` is the current publication gate. Three placeholder-CVE public posts were changed to Hugo drafts; guard against recurrence.

## Design alternatives
A. Publish everything automatically: fastest, unacceptable fabricated-claim risk.
B. **Selected:** independent security/AI intake and conservative deterministic quality gate; automatic publication only after every gate passes, otherwise review in Notion. Caps constrain damage if detection fails.
C. All posts require human approval: lowest risk but user rejected the throughput limitation.

## Data flow and component boundaries
1. A single daily Hermes script owns the run via an exclusive local lock; overlapping runs exit with a recorded reason. The launchd job stays disabled. No cron agent that writes to the blog runs concurrently.
2. Collector uses explicit security and AI source/query sets, each tagged with a fixed target category. Select recent entries (published within 72 hours, parseable timezone, non-future beyond clock skew) and canonicalize original URLs. RSS link, title, publication time, source and category form the candidate record; do not treat article text as instructions. Never mark `seen` until Notion accepts a draft or a deliberate terminal rejection is recorded. A transient failure remains retryable.
3. Select at most two candidates per category per run, de-duplicate by canonical URL and closely matching title, and avoid another article on the same event during a seven-day window. The LLM score is ranking only, not permission to publish.
4. Draft in Korean using the existing local Ollama model and save to Notion as `검토중` before any public write. Draft format separates verified facts, implications/analysis, uncertainty and a visible link to the original source. Never invent CVE IDs, quotes, dates, benchmarks or exploitability.
5. A separate verification gate receives the structured candidate and final draft. Strict auto-publish conditions: source resolves to an allowlisted original/first-party vendor, public primary advisory, official research page or original paper; HTTP fetch succeeds; publication time <=72 hours; title/category consistent; canonical source URL appears in draft; no `CVE-YYYY-XXXX`, `CVE-YYYY-0000`, made-up CVE claims, TODO/placeholder text or unsourced numeric/quote claims; minimum substantive Korean prose; no duplicate content; no executable instructions copied from source. For security CVE articles, each CVE must match the source's visible identifier and be present on the primary advisory; ambiguous claims fail closed. For AI articles, unverified model/version/performance claims fail closed. This is a conservative check, not a guarantee of factual correctness: unverifiable cases go to review.
6. Gate pass: set a distinct Notion `자동 검증 통과` state (create/confirm the database status option first), then publish via the existing GitHub publisher without weakening its `검토 완료` human gate. Limit automatic publication to one security and one AI post per day, <=2 total; no batch push on a failed quality check. Gate fail: leave `검토중`, add a visible failure reason in the run report, not a false approval.
7. Deployment verification: check GitHub Actions for the pushed commit and check exact live URL and site sitemap. Only after verifying the live artifact, update the Notion page to `게시 완료`. If deployment fails, retain recoverable status and alert; never repeat public pushes blindly.
8. Daily run report records collected/selected/drafted/gate-passed/reviewed/published counts separately by category, source URLs, gate reasons, GitHub commit and deploy state. Script-based monitoring alerts on consecutive zero output, feed failures, approval gate changes, placeholder-CVE pages and broken canonical pages. `adsense-stabilize-check` remains an independent read-only site/quality check.

## Safety and failure policy
Keep `AUTO_PUBLISH_STATUS=검토 완료` for the existing human-approved lane. A new, explicit auto-verified lane is the only automatic public path. Unknown/missing credentials, feed parse, source fetch, Notion update, DB lock or verification exception -> no automatic publication. Hard cap before writes. Rollback means setting the specific Hugo article to draft, pushing only that change, verifying that the old URL is 404 and absent from sitemap. Historic approved posts are not retroactively modified. Never claim AdSense approval from uptime checks.

## Tests and rollout
Unit tests: freshness boundary/timezone, category intake, canonical dedupe, retry-on-failure, title/source mismatch, forged CVE, missing first-party evidence, missing citation, prompt-injection text, article cap and failure-to-review. Integration tests with fixtures or mocked Notion/HTTP/LLM/Git must prove a draft cannot publish without passing all gates and a failed deploy cannot mark posted. Dry-run on real feeds without Notion/Git writes, inspect examples for both categories. First scheduled release runs quality checks with auto-publication disabled; enable capped auto-publication after dry-run and manual review of the emitted report. Verify a real GitHub Actions deployment and live URL if a qualified article exists. Lack of qualified candidates is an expected no-publish outcome, not an excuse to bypass checks.

## Acceptance criteria
Both categories have explicit nonempty recent candidates or a recorded reason for none; each real run produces category-specific counts; retries survive downstream failure; only gate-passing posts become public under the per-category daily cap; nonpassing posts remain in review; published post URL and its source link are verifiable; site monitoring flags placeholder CVE; no extra schedule or unsafe draft rewriting is active.
